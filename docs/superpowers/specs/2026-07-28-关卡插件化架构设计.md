# 《梗哥的半生》关卡插件化架构设计

> 日期：2026-07-28
> 状态：待实施
> 目标：把现有单体游戏重构为可持续增加关卡、支持多人并行开发的低耦合架构。

## 1. 背景

现有项目已经拆出了人物、世界、音频、特效、存储和部分界面模块，但核心流程仍集中在近 3800 行的主游戏文件中。该文件同时承担：

- 游戏启动与渲染循环；
- 全局运行状态；
- 关卡选择与切换；
- 人物生成与移动；
- 出拳、命中和结算；
- 各关卡专属规则；
- 页面事件与界面更新；
- 双人房间、同步和决斗规则；
- 场景资源创建与销毁。

继续在主游戏文件中增加《梗哥的半生》的十个普通关卡和一个终章，会造成多人频繁修改同一文件、合并冲突增加、关卡规则相互影响，以及资源无法可靠释放。

## 2. 架构目标

重构完成后必须满足以下要求：

1. 新增普通关卡只需增加一个独立关卡目录，不修改主循环。
2. 关卡通过自动发现机制注册，避免所有开发者共同编辑关卡列表。
3. 每个关卡只依赖稳定的关卡开发接口，不依赖页面、联机实现或其他关卡。
4. 主游戏只负责流程状态、关卡生命周期和公共系统调度。
5. 场景、人物、输入、出拳、音频、特效、计时和存档由独立公共系统提供。
6. 单人、本地多人和在线多人通过运行适配器接入，不侵入关卡规则。
7. 所有定时器、事件监听、三维对象和临时资源随关卡统一销毁。
8. 每个关卡可以独立验证生命周期、胜负规则和错误处理。
9. 多位开发者可以同时开发不同关卡，通常不会修改相同文件。

## 3. 非目标

本次重构不做以下事项：

- 不更换渲染技术和构建工具；
- 不重写现有人物模型、世界材质、音效和粒子效果；
- 不引入新的前端框架或状态管理依赖；
- 不在第一阶段删除双人代码；
- 不在架构稳定前同时开发全部新关卡；
- 不为了形式统一而重写已经独立且可复用的纯函数模块。

## 4. 总体分层

依赖方向必须保持单向：

```text
应用入口
  ↓
应用协调层
  ↓
游戏流程与关卡运行器
  ↓
关卡开发接口
  ↓
世界 / 人物 / 输入 / 出拳 / 计时 / 音频 / 特效 / 存档

页面适配器 ← 游戏状态与领域事件
联机适配器 ↔ 标准玩家指令与同步快照
具体关卡 → 仅依赖关卡开发接口
```

禁止反向依赖：

- 公共系统不得导入具体关卡；
- 关卡不得导入页面节点；
- 关卡不得导入联机模块；
- 关卡不得直接读取或修改全局运行状态；
- 关卡之间不得相互导入；
- 页面适配器不得直接改变人物和场景；
- 联机模块不得直接调用具体关卡函数。

## 5. 模块职责

### 5.1 应用入口

只负责创建公共系统、组装依赖、启动应用。入口中不包含关卡判断、页面更新和玩法逻辑。

### 5.2 应用协调器

负责接收页面命令并调用游戏流程：

- 选择关卡；
- 开始关卡；
- 暂停与继续；
- 重试；
- 返回选关；
- 进入结算。

它不负责命中判定、人物移动和具体关卡规则。

### 5.3 游戏流程状态机

唯一持有全局流程状态，状态固定为：

```text
选关 → 简报 → 进行 → 暂停 → 收尾 → 结算
```

状态机负责拒绝非法跳转。例如结算状态不能再次处理出拳，暂停状态不能推进关卡时间。

### 5.4 关卡运行器

负责管理当前关卡实例：

- 加载关卡描述；
- 创建关卡上下文；
- 调用关卡生命周期；
- 将公共输入交给当前关卡；
- 接收关卡胜负结果；
- 统一销毁关卡资源；
- 捕获关卡初始化和运行错误。

同一时间只能存在一个活动关卡实例。

### 5.5 关卡注册中心

构建时自动发现关卡目录中的描述文件，并在启动时完成校验：

- 关卡标识不可重复；
- 必需描述字段必须存在；
- 生命周期函数必须完整；
- 关卡排序和章节信息必须有效；
- 隐藏关卡不出现在选关页面，但仍可通过内部流程加载。

新增关卡不需要修改注册中心源代码。

### 5.6 关卡开发接口

关卡只能通过受控上下文使用公共能力：

| 能力 | 责任 |
| --- | --- |
| 世界 | 添加场景对象、障碍、区域和环境效果 |
| 人物 | 生成人物、查询人物、移动人物、销毁人物 |
| 出拳 | 注册可命中目标、执行命中查询、产生正确或误伤结果 |
| 输入 | 提供当前帧标准化移动和动作指令 |
| 时钟 | 提供关卡时间、倒计时和受控延时任务 |
| 音频 | 播放具名音效，不暴露底层音频实现 |
| 特效 | 震屏、顿帧、伤害闪烁、像素爆炸 |
| 事件 | 发布目标显形、误伤、胜利、失败等领域事件 |
| 资源域 | 登记对象、监听器和清理函数，关卡结束时统一销毁 |

关卡上下文不暴露渲染器、页面对象、联机连接和全局状态引用。

### 5.7 公共系统

第一阶段只拆出新关卡必需的系统：

- 输入系统；
- 世界系统；
- 人物系统；
- 出拳与命中系统；
- 游戏时钟；
- 资源域；
- 音频系统；
- 特效系统。

相机、空间网格和碰撞继续作为世界与人物系统的内部实现，不额外暴露。

### 5.8 页面适配器

页面只订阅游戏状态和领域事件，并渲染：

- 选关页面；
- 任务简报；
- 顶部信息；
- 暂停页面；
- 结算页面。

按钮点击只发送应用命令。页面不直接生成角色、不修改关卡状态、不决定胜负。

### 5.9 联机适配器

双人入口默认隐藏，现有能力暂时保留。后续联机重构时只允许传输：

- 标准玩家指令；
- 玩家状态；
- 关卡同步快照；
- 具名领域事件。

联机适配器不能感知具体关卡实现。某个关卡是否支持多人，由关卡描述声明。

## 6. 关卡包结构

每个关卡独占一个目录，至少包含：

```text
关卡目录
├── 关卡描述
├── 关卡规则
├── 场景构建
├── 关卡专属素材
└── 关卡规则验证
```

关卡描述只保存稳定元数据：

- 唯一标识；
- 标题、章节、简介和线索；
- 排序；
- 默认时长和出拳次数；
- 场景主题；
- 是否隐藏；
- 支持的玩家数量。

关卡规则只保存行为，不直接创建页面。场景构建只负责本关卡的场景对象，不处理胜负。

同一目录外的关卡不得导入该关卡内部文件。

## 7. 统一关卡生命周期

每个关卡遵守以下生命周期：

```text
创建
  ↓
装载场景与人物
  ↓
开始
  ↓
逐帧更新 / 接收出拳结果
  ↓
报告胜利或失败
  ↓
停止
  ↓
销毁全部资源
```

生命周期约束：

1. 创建阶段不得启动不可追踪的定时器。
2. 开始前不得推进关卡时间。
3. 暂停时停止关卡时钟和规则更新。
4. 胜负结果只能报告一次。
5. 销毁函数必须可重复调用且不会报错。
6. 关卡切换前必须完成上一关卡销毁。

## 8. 数据与事件流

标准单人关卡的数据流：

```text
设备输入
  ↓
输入系统生成标准指令
  ↓
游戏流程将指令交给公共系统和当前关卡
  ↓
人物移动 / 出拳查询 / 关卡规则更新
  ↓
产生领域事件和状态变化
  ↓
页面、音频、特效分别响应
```

关卡只能报告“目标命中”“误伤”“胜利”“失败”等结果，不直接控制结算页面。

## 9. 解耦规则

以下规则作为代码审查硬性标准：

1. 主循环中不得出现具体关卡标识判断。
2. 公共系统中不得出现具体关卡标识判断。
3. 关卡不得使用页面查询和全局事件监听。
4. 关卡不得直接调用浏览器存储。
5. 关卡不得直接调用联机传输。
6. 公共系统之间通过构造参数和明确方法协作，不读取对方内部状态。
7. 禁止创建包含所有对象的万能上下文；只暴露关卡实际需要的稳定能力。
8. 不新增只有一个实现的抽象层。
9. 只有两个以上关卡确认复用的逻辑，才提升为公共模块。
10. 所有共享可变状态必须有唯一所有者。

## 10. 多人协作约束

为减少合并冲突，采用以下协作方式：

- 一名开发者负责一个关卡目录；
- 关卡素材放在对应关卡目录或明确的公共素材目录；
- 新关卡通过自动发现注册，不修改公共关卡数组；
- 修改关卡开发接口必须单独提交并通知所有关卡开发者；
- 公共模块变更与具体关卡内容分开提交；
- 禁止为了单个关卡向公共系统加入专用字段；
- 临时关卡特性留在关卡内部，确认复用后再抽取。

## 11. 错误与资源处理

### 11.1 注册错误

发现重复标识、缺少字段或生命周期不完整时，开发环境直接阻止启动并指出关卡目录。

### 11.2 加载错误

关卡创建失败时：

1. 停止关卡时钟；
2. 销毁已经登记的资源；
3. 返回选关页面；
4. 显示简短错误信息；
5. 保留控制台错误供开发排查。

### 11.3 运行错误

逐帧更新发生异常时暂停当前关卡，防止错误持续刷屏或破坏全局状态，然后执行相同的安全清理流程。

### 11.4 资源清理

资源域统一追踪：

- 三维对象和材质；
- 事件监听器；
- 延时与周期任务；
- 页面临时节点；
- 关卡创建的音频；
- 关卡注册的清理回调。

## 12. 重构迁移顺序

重构采用可运行的小步提交：

### 阶段一：隔离入口

- 隐藏双人入口；
- 增加架构基线验证；
- 保证现有单人关卡仍可运行。

### 阶段二：建立骨架

- 创建游戏流程状态机；
- 创建关卡运行器；
- 创建关卡注册中心；
- 创建关卡开发接口与资源域。

暂时通过旧关卡适配器运行现有关卡，避免一次性重写。

### 阶段三：抽离公共系统

按依赖顺序迁移：

1. 游戏时钟；
2. 输入系统；
3. 出拳与命中系统；
4. 人物系统；
5. 世界与场景生命周期；
6. 页面状态渲染。

每迁移一个系统，都删除主游戏文件中的对应旧实现。

### 阶段四：迁移现有关卡

将现有单人关卡逐个迁移为独立关卡包。每迁移一关，保持玩法和表现不变。

### 阶段五：清理旧核心

- 删除旧关卡分支判断；
- 删除重复状态；
- 删除旧适配器；
- 将主游戏文件缩减为入口兼容层或完全移除。

### 阶段六：开发《梗哥的半生》

先实现一个完整教学关，验证新增关卡不需要修改主循环，再允许多人并行开发其余关卡。

### 阶段七：联机独立化

在单人关卡架构稳定后，再把现有双人逻辑迁移为独立模式适配器。入口是否恢复由功能配置控制。

## 13. 验证策略

### 13.1 架构验证

- 新建示例关卡时不修改主循环和公共系统；
- 检查关卡之间不存在相互导入；
- 检查公共系统不存在具体关卡标识判断；
- 检查页面查询只存在于页面适配器。

### 13.2 生命周期验证

每个关卡至少验证：

- 创建后可以开始；
- 暂停后不推进时间；
- 胜负只结算一次；
- 重试不会残留旧人物和定时器；
- 连续切换关卡不会增加监听器；
- 销毁后所有临时资源被释放。

### 13.3 功能验证

每个迁移步骤运行：

- 项目构建；
- 单人选关；
- 任务简报；
- 移动与出拳；
- 正确命中与误伤；
- 暂停与恢复；
- 胜负结算；
- 重试与返回选关。

## 14. 完成标准

满足以下条件才视为重构完成：

1. 主循环不包含任何具体关卡规则。
2. 新增关卡无需修改现有源文件。
3. 所有关卡通过统一生命周期运行。
4. 关卡只依赖关卡开发接口。
5. 页面、联机和关卡规则相互独立。
6. 双人入口默认隐藏，双人代码仍可恢复。
7. 现有单人玩法无功能回退。
8. 示例新关卡能够独立创建、运行、结算和销毁。
9. 架构验证、构建和关键交互检查全部通过。
