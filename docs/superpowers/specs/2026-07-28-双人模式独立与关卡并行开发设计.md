# 《梗哥的半生》双人模式独立与关卡并行开发设计

> 日期：2026-07-28
> 状态：已确认，待实施
> 目标：将不再使用的双人决斗迁为休眠独立模块，并消除新增关卡对主循环和公共分支文件的修改需求。

## 1. 已确认边界

- 双人决斗代码需要保留，但不再提供运行入口。
- 首页不显示双人入口。
- 带房间参数的链接不再启动双人模式。
- 双人模式不参加单人关卡自动注册，不进入主程序运行链路。
- 不要求双人模式在本轮迁移后仍可直接运行。
- 单人关卡现有玩法和视觉表现必须保持可用。
- 工作区已有的双人移动手感修改属于用户修改，迁移时保留其意图并移动到双人模块，不直接覆盖。

## 2. 目标依赖关系

```text
应用入口
  ↓
游戏流程与公共运行时
  ↓
关卡运行器
  ↓
当前关卡包
  ↓
稳定公共能力

休眠双人模式（无上游导入）
  ├── 决斗规则
  ├── 联机传输
  ├── 状态同步
  └── 决斗运行逻辑
```

依赖约束：

1. 主程序、关卡注册中心和单人关卡不得导入双人模式。
2. 双人模式可以依赖公共纯函数和底层渲染能力，但不得被公共层反向依赖。
3. 公共层不得通过关卡标识、场景名称或关卡专属布尔字段决定行为。
4. 不同关卡目录之间不得互相导入。

## 3. 双人模式迁移

双人代码统一归入：

```text
src/modes/duel/
├── definition.js
├── runtime.js
├── network.js
├── sync.js
├── rules.js
└── view.js
```

各文件职责：

- `definition.js`：保存决斗模式元数据，不符合单人关卡描述契约。
- `runtime.js`：保存决斗人物、集合圈、移动、攻击、结算等运行逻辑。
- `network.js`：封装房间创建、加入、离开和消息订阅。
- `sync.js`：负责决斗快照和同步载荷转换。
- `rules.js`：保留无副作用的决斗规则。
- `view.js`：保存决斗界面状态模型，不直接查询页面节点。

迁移后删除以下连接：

- 单人关卡注册中心中的双人关卡描述。
- 主游戏对房间参数和双人模式的启动处理。
- 主游戏中的决斗状态、决斗更新和决斗攻击分支。
- 单人任务弹窗、预览、结算和顶部信息中的决斗分支。
- 公共页面节点和公共样式中的决斗专属结构。

Firebase 依赖暂时保留，因为休眠模块中的联机实现仍引用它；主程序不导入双人模块，因此正常构建不会执行联机初始化。后续确认永久删除双人源码时，再连同依赖一起删除。

## 4. 单人关卡包边界

每个关卡目录可以按实际需要包含：

```text
src/levels/<level-id>/
├── definition.js
├── createLevel.js
├── world.js
├── actors.js
├── preview.js
├── constants.js
├── rules.js
└── viewModel.js
```

只要求 `definition.js` 和 `createLevel.js`。其余文件按关卡复杂度创建，不为简单关卡预建空抽象。

关卡描述负责声明：

- 稳定元数据；
- 创建关卡实例的方法；
- 可选的世界构建方法；
- 可选的人物创建方法；
- 可选的目标预览模型；
- 可选的界面展示模型。

公共层只调用这些标准入口，不判断具体关卡。

## 5. 公共能力边界

关卡运行上下文按职责分组：

```text
context
├── state
├── clock
├── world
├── actors
├── combat
├── effects
├── audio
├── ui
└── resources
```

约束如下：

- 分组对象只暴露稳定操作，不暴露页面节点、全局变量或其他关卡状态。
- 寺庙阴影、血月狼爪等专属能力迁回对应关卡，通过公共的场景对象、特效和音频基础能力组合实现。
- 单个关卡需要的新行为先留在关卡内部；至少两个关卡确认复用后才进入公共层。
- 主循环只调度通用移动、时间、攻击和关卡生命周期。

## 6. 世界、人物和预览扩展

当前集中判断改为默认实现加关卡覆盖：

```text
关卡描述提供实现？
  ├── 是：调用关卡实现
  └── 否：调用公共默认实现
```

具体规则：

- 世界构建器只保留可复用的基础地面、边界、灯光和障碍辅助函数。
- 寺庙、图书馆、游戏房、血月等场景组装迁入各自关卡目录。
- 公共人物模块只保留低多边形人物、狼人等可复用人物原语。
- 某关卡如何选择人物原语，由该关卡自己的创建方法决定。
- 目标预览渲染器只渲染标准预览模型，不识别关卡标识。

## 7. 关卡交互协议

继续保留当前关卡实例的四个生命周期方法：

```text
start
update
handleAction
dispose
```

为避免任意字符串静默失效：

- 公共动作名称集中定义并由关卡契约校验。
- 关卡描述声明自己处理的动作集合。
- 运行器只向声明支持该动作的关卡派发。
- 未声明动作在开发环境直接报出关卡标识和动作名称。
- 关卡结果使用稳定结构返回，不允许直接操作结算页面。

本轮不引入新的状态管理依赖或类型工具链。

## 8. 多人并行开发规则

完成后，新增关卡的正常改动范围必须限制在：

```text
src/levels/<new-level>/**
tests/levels/<new-level>/**
```

以下情况才允许修改公共层：

- 确认存在两个以上关卡共用的新基础能力；
- 关卡契约需要新增通用生命周期语义；
- 修复公共系统缺陷。

公共能力变更必须与具体关卡内容分开提交。一个关卡不得向公共上下文增加带有关卡名称的字段。

## 9. 自动架构验证

增加可重复执行的架构测试，至少验证：

1. 单人关卡自动注册中不存在双人模式。
2. 主程序和公共层不导入 `modes/duel`。
3. 不同关卡目录之间不存在互相导入。
4. 公共核心文件中不存在已知关卡标识判断。
5. 所有可注册关卡都通过描述和实例契约校验。
6. 新增一个最小测试关卡时无需修改注册中心。
7. 生产构建不包含双人联机模块入口。

架构测试用于保护边界，不通过复杂语法分析器实现；使用现有测试工具读取源文件并检查明确规则即可。

## 10. 迁移顺序

迁移采用功能完整的小步提交：

1. 建立架构约束测试，固定允许和禁止的依赖。
2. 将双人决斗移入休眠独立模块，断开主程序和注册中心连接。
3. 把关卡专属配置迁回各关卡目录。
4. 把世界构建改为默认实现加关卡覆盖。
5. 把人物创建改为默认实现加关卡覆盖。
6. 把目标预览和界面模型改为标准数据渲染。
7. 收窄关卡运行上下文并校验动作协议。
8. 删除主循环剩余的具体关卡行为判断。
9. 用最小示例关卡验证只新增目录即可完成注册、运行和销毁。
10. 运行完整测试、生产构建和关键页面检查。

每一步完成后都必须保持单人游戏可构建、现有关卡测试通过，并使用中文提交信息。

## 11. 完成标准

只有同时满足以下条件才视为迁移完成：

1. 双人决斗源码集中在独立模式目录，主程序对它没有导入和运行入口。
2. 双人决斗不再出现在关卡注册结果中。
3. 主循环不包含双人或具体单人关卡规则。
4. 公共世界、人物、预览和界面模块不判断具体关卡。
5. 不同关卡之间不存在源码依赖。
6. 新增不同场景和特殊角色的关卡不需要修改主循环。
7. 普通关卡开发者只修改自己的关卡目录和对应测试。
8. 架构测试能够阻止边界回退。
9. 现有单人关卡测试和生产构建通过。
10. 工作区原有用户修改未被覆盖或丢失。
