# 关卡强隔离与共享运行时拆分设计

## 背景

当前项目已经完成第一轮关卡插件化：

- 双人决斗已迁入 `src/modes/duel/`，活动应用不再引用。
- 四个单人关卡拥有独立的规则、角色入口、场景入口和预览入口。
- 注册中心自动发现关卡，动作与扩展名称受到契约校验。
- 共享运行时不再按照关卡标识分派。

但是完整关卡开发仍未彻底隔离：

- 四个场景的具体实现仍集中在 `src/world/createWorldBuilder.js`。
- `src/game.js` 仍认识宿舍电脑、血月猎杀界面、血月主题和狼人动画。
- 关卡专属样式仍位于全局样式文件。
- `src/game.js` 同时负责生命周期、输入、移动、战斗、界面和结算。
- 已有游戏阶段状态机尚未接入主运行时。

因此，目前只能支持普通规则开发并行，不能保证场景、特殊界面和特殊动画的完整并行开发。

## 目标

1. 不同开发者修改不同关卡时，默认不修改同一个文件。
2. 新增普通关卡不需要修改主运行时、注册中心、其他关卡或全局样式。
3. 单个关卡完整拥有其规则、场景、角色、特殊动画、特殊界面、音效调用、常量和样式。
4. 共享运行时只提供稳定的通用能力，不认识具体关卡标识和关卡特征。
5. 将 `src/game.js` 缩减为启动和依赖组装入口，目标为 150 至 250 行。
6. 使用自动化架构测试约束依赖方向，避免后续开发重新产生耦合。

## 非目标

- 不恢复或重新启用双人决斗。
- 不改变现有关卡玩法、数值、画风和操作手感。
- 不引入新的状态管理框架、依赖注入框架或界面框架。
- 不保证多人同时修改同一个关卡或同一个共享协议时完全没有冲突。
- 不为尚未出现的扩展需求预先设计通用抽象。

## 方案选择

采用“关卡垂直切片加稳定共享内核”方案。

没有选择仅拆分 `game.js` 的方案，因为拆文件不能消除关卡资源仍位于共享文件的问题。也不采用独立软件包或沙箱插件方案，因为当前项目规模不需要额外构建边界和发布流程。

## 目标架构

### 关卡垂直切片

每个关卡目录完整拥有该关卡的变化点：

```text
src/levels/<level-id>/
├── definition.js
├── createLevel.js
├── world.js
├── actors.js
├── animations.js
├── view.js
├── preview.js
├── audio.js
├── constants.js
└── styles.css
```

只创建实际需要的文件。没有特殊动画、界面或音效的关卡不创建对应模块。

各文件职责：

- `definition.js`：元数据、动作声明和扩展注册。
- `createLevel.js`：玩法状态与生命周期，不直接操作全局界面。
- `world.js`：完整场景搭建并返回该关卡的 `sceneData`。
- `actors.js`：玩家和非玩家角色工厂。
- `animations.js`：角色专属动画回调。
- `view.js`：关卡专属弹层、主题和界面事件。
- `preview.js`：选关页目标预览。
- `audio.js`：关卡专属音效调用。
- `constants.js`：仅由本关卡使用的数值。
- `styles.css`：仅由本关卡使用的样式。

关卡目录之间禁止相互导入。

### 稳定共享内核

共享代码按职责拆分：

```text
src/game.js
src/runtime/createGameSession.js
src/runtime/createGameLoop.js
src/systems/createActorSystem.js
src/systems/createCombatSystem.js
src/ui/createGameUiController.js
src/world/createWorldBuilder.js
```

- `game.js`：创建渲染器、相机和各系统，启动游戏。
- `createGameSession.js`：拥有当前场景、玩家、角色集合、关卡状态和游戏阶段。
- `createGameLoop.js`：控制每帧更新顺序与渲染。
- `createActorSystem.js`：通用移动、漫游、替身、角色分离和动画调度。
- `createCombatSystem.js`：攻击冷却、命中查找、消散和结算触发。
- `createGameUiController.js`：选关、任务、暂停、结算和通用抬头界面。
- `createWorldBuilder.js`：只搭建通用灯光、地面、墙体和障碍能力，不包含具体关卡场景。

粒子效果继续由现有特效系统承担，不单独增加只有一个调用方的新抽象。

### 保留现有契约位置

继续使用现有文件，避免仅为目录整齐进行无业务价值的搬迁：

- `src/levels/actions.js`
- `src/levels/levelContract.js`
- `src/levels/createLevelContext.js`
- `src/levels/levelRunner.js`

## 关卡契约

### 场景扩展

`createWorld(worldContext)` 负责完整关卡场景，并返回关卡私有资源：

```js
function createWorld(worldContext) {
  return {
    // 只由本关卡读取的场景资源
  };
}
```

返回值统一保存为 `sceneData`。宿舍电脑位置、承天寺月光点和血月提示物均不得出现在共享会话状态中。

`worldContext` 只提供通用能力：

- 场景实例
- 三维库
- 基础光源
- 障碍登记
- 通用墙体创建
- 纹理工具
- 随机数

不再提供 `buildGamingRoom`、`buildLibrary`、`buildTempleCourtyard` 或 `buildBloodmoonStreet`。

### 角色扩展

角色工厂可以在角色对象上附加可选动画能力：

```js
actor.animations = {
  update(actor, frame),
  attack(actor, frame),
  cheer(actor, frame),
};
```

共享角色系统只调用存在的回调，不检查狼人、披风或其他关卡特征。普通角色继续使用共享默认动画。

### 界面扩展

共享界面控制器提供动态弹层容器和主题数据属性：

```js
ui.showOverlay(key, options);
ui.hideOverlay(key);
ui.setTheme(theme);
ui.clearLevelView();
```

弹层按照 `key` 动态创建，不再硬编码猎杀介绍和猎杀卡片。关卡的 `view.js` 负责内容、样式类名和事件回调。

共享抬头界面只设置通用主题值：

```js
hud.dataset.theme = viewModel.theme ?? "";
```

共享运行时不得出现 `bloodmoon`、`huntIntro`、`huntCard` 等关卡名称。

### 音效

普通攻击、命中、失败和胜利音效继续由共享音效系统处理。关卡专属音效由关卡 `audio.js` 调用共享的底层音频能力。

玩家从任务说明进入正式游戏时，主运行时发送通用 `beginPlay` 动作。需要开场音效或演出的关卡自行处理该动作。

### 关卡上下文

将当前扁平能力对象按稳定领域分组：

```js
{
  definition,
  scope,
  sceneData,
  time,
  actors,
  movement,
  combat,
  world,
  ui,
  audio,
  random
}
```

上下文及各能力分组均冻结。关卡只能调用公开能力，不能直接读取主运行时模块变量。

## 状态与数据流

加载关卡：

1. 游戏会话销毁上一关卡及其资源域。
2. 注册中心提供关卡定义。
3. 通用世界构建器创建基础场景。
4. 关卡 `createWorld` 创建专属场景并返回 `sceneData`。
5. 关卡角色扩展创建玩家和非玩家角色。
6. 关卡运行器使用分组上下文创建关卡实例。
7. 界面控制器展示任务说明和关卡预览。

进入游戏：

1. 界面控制器请求会话从说明阶段进入游玩阶段。
2. 会话通过游戏阶段状态机验证转换。
3. 关卡运行器收到 `beginPlay` 动作。
4. 主循环开始更新关卡、角色、战斗、特效和界面。

结束关卡：

1. 战斗系统或关卡请求通用结算。
2. 会话进入结算等待阶段。
3. 会话进入结果阶段并生成通用结果数据。
4. 界面控制器展示结果。
5. 离开关卡时清理关卡界面、场景和资源域。

## 游戏阶段

主运行时必须使用现有 `src/core/gamePhase.js`，禁止直接写入任意字符串状态。

现有成功和失败状态统一表示为结果阶段，成功与否保存在结果数据中，而不是继续作为两个额外阶段。所有状态变化通过 `transitionPhase` 完成。

## 样式加载

注册中心使用构建工具的自动发现能力加载 `src/levels/*/styles.css`。关卡定义不直接导入样式，避免纯运行时测试解析样式文件。

迁移完成后，全局样式只保留通用布局和组件样式。血月、猎杀、宿舍等关卡专属选择器必须位于对应关卡目录。

## 错误处理

- 未知动作和未知扩展继续在关卡定义校验阶段报错。
- 关卡实例异常继续由关卡运行器捕获，并销毁当前关卡资源。
- 非法游戏阶段转换立即抛错，测试环境必须暴露错误。
- 关卡场景未返回资源时，`sceneData` 使用空对象。
- 可选动画和可选界面能力不存在时使用通用默认行为。
- 清理操作必须可重复调用，不得重复释放共享缓存资源。

## 并行开发规则

普通关卡开发者只修改：

- `src/levels/<level-id>/`
- `tests/levels/<level-id>*.test.js`

只有新增通用引擎能力时才允许修改共享契约或运行时。共享协议变更必须独立提交，并先于依赖该协议的关卡提交合并。

不同关卡开发允许：

- 同时修改各自场景。
- 同时修改各自角色和特殊动画。
- 同时修改各自界面和样式。
- 同时修改各自玩法、常量和测试。

以下工作仍需要协调：

- 同时修改同一个关卡。
- 同时新增或修改同一个共享动作或扩展。
- 修改通用输入、碰撞、战斗和渲染行为。

## 自动化边界检查

架构测试必须验证：

1. 不同关卡目录之间没有互相导入。
2. 活动应用没有导入休眠双人模式。
3. 共享运行时不包含具体关卡标识。
4. 共享运行时不包含关卡专属角色特征、弹层名称和主题名称。
5. `createWorldBuilder.js` 不导出或包含具体关卡场景构建器。
6. 关卡专属常量不位于全局配置。
7. 关卡专属样式不位于全局样式文件。
8. 所有关卡定义通过动作和扩展白名单校验。
9. 样例关卡只依赖公开契约即可加载。

## 迁移顺序

### 第一阶段：关闭剩余关卡泄漏

- 宿舍电脑资源迁入宿舍 `sceneData`。
- 狼人动画迁入血月角色动画。
- 血月猎杀界面和主题迁入血月界面模块。
- 开场狼嚎改为通用 `beginPlay` 动作。

### 第二阶段：场景完全归属关卡

- 依次迁移宿舍、图书馆、承天寺和血月场景实现。
- 迁移对应常量和专属样式。
- 将共享世界构建器缩减为通用能力。

每个关卡场景迁移形成独立、可运行、可回退的提交。

### 第三阶段：拆分共享运行时

- 接入游戏阶段状态机。
- 提取游戏会话和主循环。
- 提取角色系统和战斗系统。
- 提取界面控制器。
- 缩减 `game.js` 为依赖组装入口。

每次提取保持玩法行为不变，并在提交前运行完整测试和生产构建。

### 第四阶段：强化架构防回退

- 增加源码边界测试。
- 更新独立样例和并行开发指南。
- 执行完整测试、生产构建和源码扫描。

## 验收标准

满足以下条件才视为迁移完成：

- `game.js` 不超过 250 行，只负责启动和组装。
- `createWorldBuilder.js` 不包含任何具体关卡场景。
- `game.js`、共享系统和共享界面中不存在具体关卡名称。
- 所有关卡专属场景、动画、界面、常量和样式位于各自目录。
- 新增样例关卡不需要修改任何共享运行时代码。
- 四个现有关卡玩法和操作手感保持不变。
- 双人决斗仍为未启用独立模块。
- 全部自动化测试通过。
- 生产构建成功。
- 工作区只保留用户原有且未授权修改的文件变更。

## 并行能力结论

完成本设计后，可以在代码边界和自动化检查层面保证不同关卡的完整并行开发。保证范围覆盖规则、场景、角色、动画、界面、音效、常量、样式和测试。

共享引擎协议仍是有意保留的协调点。任何系统都无法在多人同时修改同一共享契约时保证零冲突，因此该类改动通过独立提交和串行合并处理。
